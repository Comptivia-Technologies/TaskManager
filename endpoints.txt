================================================================================
                    LOCAL DEVELOPMENT SETUP
================================================================================

Prerequisites:
- .NET 8 SDK
- Node.js 18+
- PostgreSQL (local)
- Docker Desktop (for RabbitMQ)

PostgreSQL databases required:
- WorkflowManagement  (WorkflowManagement.API, SLAConfiguration.API, Workload.API,
                       WorkflowService, WorkloadService, SLAManagerService)
- TaskService           (TaskService)
- PriorityRuleEngine    (PriorityRuleEngine.API)

Update connection strings in each service's appsettings.Local.json or
appsettings.Development.json with your local postgres username/password.

--------------------------------------------------------------------------------
Step 1: Start RabbitMQ
--------------------------------------------------------------------------------

From the repo root:

  docker compose -f docker-compose.local.yml up -d

RabbitMQ ports (mapped to avoid conflicts with a local RabbitMQ install):
- AMQP:       localhost:5673   (default 5672 inside container)
- Management: localhost:15673  (default 15672 inside container)

Management UI: http://localhost:15673
Credentials:   guest / guest

The local image includes the delayed-message exchange plugin (used for SLA
timeouts and scheduled events).

Stop RabbitMQ:

  docker compose -f docker-compose.local.yml down

--------------------------------------------------------------------------------
Step 2: Start backend services
--------------------------------------------------------------------------------

Event-driven services MUST use the "Local" launch profile so
appsettings.Local.json loads with EventBus:Provider = RabbitMQ.

Run each in a separate terminal from the repo root:

  cd backend/WorkflowManagement.API && dotnet run
  cd backend/SLAConfiguration.API && dotnet run
  cd backend/PriorityRuleEngine.API && dotnet run --launch-profile Local
  cd backend/Workload.API && dotnet run
  cd backend/APIGateway && dotnet run --launch-profile Local
  cd backend/TaskService && dotnet run --launch-profile Local
  cd backend/WorkflowService && dotnet run --launch-profile Local
  cd backend/SLAManagerService && dotnet run --launch-profile Local
  cd backend/WorkloadService && dotnet run --launch-profile Local

Service ports:

  Service                  Port    RabbitMQ    Notes
  ---------------------------------------------------------------------------
  WorkflowManagement.API   5000    No          CRUD (workflows, teams, tasks)
  SLAConfiguration.API     5002    No          SLA config CRUD
  Workload.API             5003    No          Workload queries
  APIGateway               5004    Yes         Single entry point for APIs
  TaskService              5005    Yes         Task create / stage / status
  WorkflowService          5006    Yes         Workflow selection, stage flow
  SLAManagerService        5007    Yes         SLA deadlines and overdue
  WorkloadService          5008    Yes         Task assignment
  PriorityRuleEngine.API   5010    Yes         Priority evaluation

All external API calls go through APIGateway at http://localhost:5004.

--------------------------------------------------------------------------------
Step 3: Start frontend
--------------------------------------------------------------------------------

  cd frontend/workflow
  npm install
  npm run start:dev

Frontend: http://localhost:3000
API base: http://localhost:5004 (set in .env.development as REACT_APP_API_URL)

--------------------------------------------------------------------------------
Startup order (recommended)
--------------------------------------------------------------------------------

1. PostgreSQL
2. RabbitMQ (docker compose)
3. WorkflowManagement.API (other services depend on it)
4. Remaining CRUD APIs (SLAConfiguration, PriorityRuleEngine, Workload)
5. Event-driven microservices (TaskService, WorkflowService, SLAManager,
   WorkloadService)
6. APIGateway (last backend service)
7. Frontend

After create-task, wait 2-5 seconds for RabbitMQ-driven orchestration
(workflow selection -> priority -> SLA -> assignment -> stage start).

================================================================================
                         RABBITMQ EVENT BUS
================================================================================

Local development uses RabbitMQ instead of AWS EventBridge. Production/QA
still use AWS (or Azure/GCP) via EventBus:Provider in appsettings.

Provider selection (EventBusFactory):
- appsettings.Local.json sets "Provider": "RabbitMQ" for Local environment
- Override at runtime: EVENTBUS_PROVIDER=RabbitMQ

Shared config (appsettings.Local.json in each event service):

  "EventBus": {
    "Provider": "RabbitMQ",
    "RabbitMQ": {
      "HostName": "localhost",
      "Port": 5673,
      "UserName": "guest",
      "Password": "guest",
      "VirtualHost": "/",
      "ServicePrefix": "task-manager-local",
      "ExchangeName": "task-manager-events",
      "PrefetchCount": 10
    }
  }

Exchange:
- Name: task-manager-local-task-manager-events (ServicePrefix + ExchangeName)
- Type: x-delayed-message (supports scheduled/delayed events for SLA timeouts)

Queues (per service, prefixed with task-manager-local-):
- task-manager-local-task-service       (TaskService)
- task-manager-local-workflow-service   (WorkflowService)
- task-manager-local-sla-service        (SLAManagerService)
- task-manager-local-workload-service   (WorkloadService)
- task-manager-local-priority-service   (PriorityRuleEngine)

Routing keys / detail types (EventBusConstants):
- TaskCreated, TaskCreatedForPriority, PriorityAssigned
- WorkflowSelected, SLAConfigured, TaskAssigned
- TaskStageStarted, TaskStageCompleted, TaskStageEscalated
- TaskStageEscalationTriggered, TaskStageReassignmentNeeded
- TaskOverdue, TaskStatusUpdated, TaskCompleted

Example flow after POST /api/task-service:
  TaskService publishes TaskCreated
    -> PriorityRuleEngine (priority)
    -> WorkflowService (workflow selection)
    -> SLAManagerService (SLA deadline)
    -> WorkloadService (assignment)
    -> TaskService (stage start)

Implementation: backend/Shared/Shared.Messaging/RabbitMQEventBus.cs
Docker image:   docker/rabbitmq/Dockerfile (rabbitmq:3.13-management + delayed plugin)

Verify RabbitMQ is working:
- Management UI at http://localhost:15673 shows the exchange and queues
- Service logs show: "RabbitMQEventBus initialized. Host=localhost:5673 ..."
- After create-task, queues receive messages and task status progresses

================================================================================
                    TASK OPERATIONS API DOCUMENTATION
================================================================================

Complete guide for task creation, update, escalation, completion, and retrieval.

================================================================================
1. CREATE TASK
================================================================================

Local Endpoint:
POST http://localhost:5004/api/task-service

Deployed Endpoint:
POST https://api.workflowautomation.enginuo.com/api/task-service

Payload:
{
  "taskName": "Fix login bug",
  "description": "Users cannot login with email",
  "priority": "High",
  "taskType": "Bug",
  "taskData": {
    "customField": "value"
  }
}

Payload Fields:
- taskName (required): Task name
- description (optional): Task description
- priority (required): Priority level (e.g., "High", "Medium", "Low", "Critical")
- taskType (required): Type of task (e.g., "Bug", "Feature", "Task")
- taskData (optional): Additional custom data as key-value pairs

Output:
{
  "taskId": "d1a4a98a-57fc-4442-a7cd-95c4c0fe7ecb",
  "message": "Task creation initiated. Processing asynchronously. Use GET /api/task-service/{taskId} to retrieve full details."
}

Status Code: 202 Accepted

Note: 
- Task creation triggers event-driven orchestration via RabbitMQ locally
  (workflow selection, SLA configuration, assignment)
- Wait a few seconds after creation before retrieving full details
- Use the returned taskId to get task details

================================================================================
2. UPDATE TASK STATUS
================================================================================

Local Endpoint:
PUT http://localhost:5004/api/task-service/status/{taskId}

Deployed Endpoint:
PUT https://api.workflowautomation.enginuo.com/api/task-service/status/{taskId}

Example:
PUT http://localhost:5004/api/task-service/status/d1a4a98a-57fc-4442-a7cd-95c4c0fe7ecb

Payload (String - Recommended):
{
  "status": "Completed"
}

Payload (Numeric - Backward Compatible):
{
  "status": 5
}

Valid Status Values:

String          Numeric    Description
------------------------------------------------------------------------
"Created"       0          Task created, awaiting workflow selection
"WorkflowSelected" 1       Workflow has been selected
"SLAConfigured" 2          SLA has been configured
"Assigned"      3          Task assigned to a member
"InProgress"    4          Task is in progress
"Completed"     5          Task is completed
"Overdue"       6          Task has passed SLA deadline
"Cancelled"     7          Task has been cancelled
"Escalated"     8          Task has been escalated

Output:
{
  "message": "Task status updated to Completed"
}

Status Code: 200 OK

Error Responses:
- 404 Not Found: Task with ID not found
- 400 Bad Request: Invalid status value
- 500 Internal Server Error: Server error

================================================================================
3. COMPLETE STAGE
================================================================================

Local Endpoint:
POST http://localhost:5004/api/task-service/complete-stage/{taskId}

Deployed Endpoint:
POST https://api.workflowautomation.enginuo.com/api/task-service/complete-stage/{taskId}

Example:
POST http://localhost:5004/api/task-service/complete-stage/d1a4a98a-57fc-4442-a7cd-95c4c0fe7ecb

Payload: None

Output:
{
  "message": "Stage completed successfully. Task will transition to the next stage."
}

Status Code: 200 OK

Note:
- Completes the current stage and transitions to the next stage
- Publishes TaskStageCompletedEvent which triggers stage transition
- Increments member's completion count
- If no next stage exists, task is marked as completed

Error Responses:
- 404 Not Found: Task with ID not found
- 400 Bad Request: Cannot complete stage (e.g., no current stage, already completed, no next stage)
- 500 Internal Server Error: Server error

================================================================================
4. COMPLETE TASK
================================================================================

There is no dedicated /complete-task endpoint. Use one of:

Option A — set status directly (recommended):
PUT http://localhost:5004/api/task-service/status/{taskId}
{
  "status": "Completed"
}

Option B — complete the final stage:
POST http://localhost:5004/api/task-service/complete-stage/{taskId}
If no next stage exists, the task is marked completed automatically.

================================================================================
5. ESCALATE STAGE
================================================================================

Local Endpoint:
POST http://localhost:5004/api/task-service/escalate-stage/{taskId}

Deployed Endpoint:
POST https://api.workflowautomation.enginuo.com/api/task-service/escalate-stage/{taskId}

Example:
POST http://localhost:5004/api/task-service/escalate-stage/d1a4a98a-57fc-4442-a7cd-95c4c0fe7ecb

Payload (Optional):
{
  "reason": "Unable to resolve issue, needs expert review"
}

Output:
{
  "message": "Stage escalated successfully. Task will transition to the next stage."
}

Status Code: 200 OK

Note:
- Escalates the current stage to the next stage
- Unlike CompleteStage, this does NOT increment member's completion count
- Used when a member cannot handle the task and needs to pass it to the next stage
- If no next stage exists, task is marked as completed

Error Responses:
- 404 Not Found: Task with ID not found
- 400 Bad Request: Cannot escalate stage (e.g., no current stage, no next stage)
- 500 Internal Server Error: Server error

================================================================================
6. GET ENRICHED TASK BY ID
================================================================================

Local Endpoint:
GET http://localhost:5004/api/tasks/{taskId}

Deployed Endpoint:
GET https://api.workflowautomation.enginuo.com/api/tasks/{taskId}

Example:
GET http://localhost:5004/api/tasks/d1a4a98a-57fc-4442-a7cd-95c4c0fe7ecb

Payload: None

Output:
{
  "taskId": "d1a4a98a-57fc-4442-a7cd-95c4c0fe7ecb",
  "taskName": "Fix login bug",
  "description": "Users cannot login with email",
  "status": "InProgress",
  "priority": "High",
  "workflowId": 1,
  "workflowName": "Bug Fix Workflow",
  "stageName": "L1 Support",
  "assignedToMemberId": 25,
  "assignedToMemberName": "John Doe",
  "createdAt": "2026-01-21T10:00:00Z"
}

Status Code: 200 OK

Output Fields:
- taskId: Unique task identifier (UUID)
- taskName: Name of the task
- description: Task description
- status: Task status (string format: "Created", "InProgress", "Completed", etc.)
- priority: Task priority level
- workflowId: ID of the assigned workflow
- workflowName: Name of the assigned workflow (enriched from WorkflowManagement.API)
- stageName: Name of the current stage (enriched from WorkflowManagement.API)
- assignedToMemberId: ID of the assigned member
- assignedToMemberName: Full name of the assigned member (enriched from WorkflowManagement.API)
- createdAt: Task creation timestamp

Note:
- This endpoint enriches task data from both TaskService and WorkflowManagement.API
- Includes workflow name, assignee name, and stage name for better readability
- Status is returned as string (not numeric)

Error Responses:
- 404 Not Found: Task with ID not found
- 500 Internal Server Error: Server error

================================================================================
8. GET TASKS ASSIGNED TO MEMBER BY USER ID
================================================================================

Resolves Members.UserId (e.g. auth subject from token) to MemberId in the current organization,
then returns tasks currently assigned to that member (AssignedToMemberId). Same task shape as
other WorkflowManagement task list responses.

Local Endpoint:
GET http://localhost:5004/api/tasks/user/{userId}

Deployed Endpoint:
GET https://api.workflowautomation.enginuo.com/api/tasks/user/{userId}

Example:
GET http://localhost:5004/api/tasks/user/auth0|abc123-or-firebase-uid

Path parameter:
- userId (required): Must match Members.UserId for a member in the current organization.
  URL-encode the value if it contains reserved characters.

Payload: None

Headers (typical):
- X-Organization-Id: <organization-guid> (required for organization-scoped resolution; same as other WorkflowManagement APIs)

Output:
Same JSON array of task objects as section 6 (TaskReadDto): taskId, taskName, description, status,
priority, dueDate, workflowId, stageId, stageName, assignedToMemberId, assignedToMemberName,
completedByMemberIds, escalatedByMemberIds, isOverdue, createdAt, updatedAt.

Status Code: 200 OK (array may be empty if the member has no assigned tasks)

Error Responses:
- 400 Bad Request: userId missing or whitespace
- 401 Unauthorized: Organization context required (e.g. missing X-Organization-Id when enforced)
- 404 Not Found: No member exists with that UserId in the current organization
- 500 Internal Server Error: Server error

Note:
- This is "currently assigned to me" only. After reassignment to another member, the task no
  longer appears here; stage completions by a member are tracked via completedByMemberIds on the
  task and exposed on GET /api/tasks/member/summary/{memberId}.
- Routed through API Gateway to WorkflowManagement.API when using the gateway base URL above.

================================================================================
COMPLETE TASK LIFECYCLE EXAMPLE
================================================================================

Step 1: Create Task
POST http://localhost:5004/api/task-service
{
  "taskName": "Fix login bug",
  "description": "Users cannot login",
  "priority": "High",
  "taskType": "Bug"
}

Response: { "taskId": "d1a4a98a-57fc-4442-a7cd-95c4c0fe7ecb", ... }

Step 2: Wait for Orchestration (2-5 seconds)
The system automatically:
- Selects workflow
- Configures SLA
- Assigns to member
- Starts in first stage

Step 3: Get Enriched Task Details
GET http://localhost:5004/api/tasks/d1a4a98a-57fc-4442-a7cd-95c4c0fe7ecb

Response: { "taskId": "...", "status": "InProgress", "workflowName": "...", ... }

Step 4: Update Status (if needed)
PUT http://localhost:5004/api/task-service/status/d1a4a98a-57fc-4442-a7cd-95c4c0fe7ecb
{
  "status": "InProgress"
}

Step 5: Complete Stage (when work is done)
POST http://localhost:5004/api/task-service/complete-stage/d1a4a98a-57fc-4442-a7cd-95c4c0fe7ecb

Task transitions to next stage automatically

Step 6: Escalate Stage (if cannot handle)
POST http://localhost:5004/api/task-service/escalate-stage/d1a4a98a-57fc-4442-a7cd-95c4c0fe7ecb
{
  "reason": "Needs expert review"
}

Task transitions to next stage without incrementing completion count

Step 7: Get All Tasks
GET http://localhost:5004/api/tasks

Returns all tasks with enriched data

Step 8: Get Tasks Assigned to Current User (by Members.UserId)
GET http://localhost:5004/api/tasks/user/{userId}

Returns tasks where AssignedToMemberId matches the member linked to that UserId in the current org.

================================================================================
ERROR RESPONSE FORMAT
================================================================================

All endpoints return errors in this format:

{
  "error": "Error message here"
}

Common Status Codes:
- 200 OK - Success
- 202 Accepted - Task creation initiated (async processing)
- 204 No Content - Success (no response body)
- 400 Bad Request - Invalid input
- 401 Unauthorized - Authentication or organization context required
- 404 Not Found - Resource not found
- 500 Internal Server Error - Server error
